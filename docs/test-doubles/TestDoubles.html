Test doubles

A test double is a value, object, or function used in place of a production collaborator or required placeholder while testing a specific behavior.

The term comes from cinema “stunt doubles”. It is an umbrella term, not one particular implementation technique. Ordinary representative domain data is a fixture, not automatically a test double.

Based on the test-doubles section of Daniel Moka’s Transform Your Craft with TDD (pages 72–84), with TypeScript examples.

🧭 Taxonomy at a glance

TestDouble
├─ Dummy   → Fills an unused required slot
├─ Stub    → Supplies a controlled answer
├─ Fake    → Provides a simplified working implementation
├─ Spy     → Records interactions
└─ Mock    → Verifies an interaction contract
Classify by use, not construction. The same test helper or vi.fn() can play different roles. What matters is why the test uses it and what the test observes.

🧩 Dummy

Intent

Fill a required parameter that is never used.

Key Traits

  • No behavior used by the scenario
  • No assertions about the dummy
  • Can be a dummy value or object; a fail-loud object makes accidental use obvious

Use When

  • The system under test requires a dependency that the selected path never uses

Red Flag

  • The test starts depending on it

📤 Stub

Intent

Provide predefined answers to control execution paths.

Key Traits

  • Input → output
  • No interaction verification
  • Passive

Use When

  • You need deterministic data
  • You want to avoid slow or unstable dependencies

Red Flag

  • You start asserting how many times it was called

🏗️ Fake

Intent

Provide a working but simplified implementation.

Key Traits

  • Real logic
  • Often in-memory
  • Deterministic and fast

Use When

  • Replacing infrastructure (DB, cache, queue)
  • You want realistic behavior without real I/O

Red Flag

  • Fake becomes as complex as production code

👀 Spy

Intent

Observe what happened after execution.

Key Traits

  • Records calls and arguments
  • Assertions happen after execution
  • Flexible

Use When

  • Verifying side effects
  • Observing interactions without strict contracts

Red Flag

  • Assertions depend heavily on internal implementation

🔒 Mock

Intent

Verify a required interaction contract.

Key Traits

  • Exact collaboration is part of the expected outcome
  • Expected calls are verified as part of the outcome
  • More coupled to the collaboration protocol

Use When

  • Testing collaboration rules
  • Preventing forbidden calls
  • Protocol or orchestration testing

Red Flag

  • Refactors break tests without behavior change

🔍 Spy vs Mock

Both may record calls. A spy exposes what happened so the test can inspect it; a mock makes a particular call protocol part of the test’s required outcome.

Aspect Spy Mock
Purpose Expose interaction history for inspection Verify a required interaction protocol
Typical assertion A selected recorded value or event Exact calls, arguments, order, or absence
Best fit Observe an indirect output afterward The collaboration itself is the outcome
Main risk Asserting too much recorded detail Coupling the test to implementation structure

🔄 Mock vs Fake

Question Fake Mock
What does it provide?A small working implementationA required interaction protocol
What does the test usually assert?Result or resulting stateCalls, arguments, order, or absence of calls
Best fitStateful or repository-like portsNarrow wire boundaries where the call itself matters
Main riskDuplicating too much production behaviorCoupling the test to implementation details

Prefer a fake when you can prove behavior through an observable outcome or state change. Use a mock when an exact collaboration is genuinely the contract, such as issuing one payment command or publishing one wire message.

⚠️ Common Misconceptions

“Mocks are bad”

→ Over-mocking is bad. Mocks are valid when enforcing contracts.

“Unit tests must mock everything”

→ Unit tests isolate behavior, not necessarily classes.

“Stub = Mock”

→ Stub controls data. Mock enforces interaction rules.

“Anything created by a mocking library is a mock”

→ Libraries create test helpers. The role comes from how the test uses the helper.

🧠 Practical Heuristic

Choose the smallest role that expresses the behavior under test:

  • Required but unused in this path? → Dummy
  • Need one controlled answer? → Stub
  • Need realistic, reusable stateful behavior without real I/O? → Fake
  • Need to inspect what happened afterward? → Spy
  • Is an exact call itself part of the contract? → Mock

🧠 Mental Model

Good tests describe what the system does,

not how it is implemented.

The more your test doubles encode implementation details, the more fragile your tests become.
