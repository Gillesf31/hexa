Test doubles

A test double is any object that replaces a real collaborator in a test, in order to control behavior, observe interactions, or isolate a scenario.

The term comes from cinema “stunt doubles”. It is an umbrella term, not a specific technique.

🧭 Taxonomy at a glance

TestDouble
├─ Dummy   → Just there to be able to run code
├─ Stub    → Returns data
├─ Fake    → Works as code but simplified
├─ Spy     → Records interactions
└─ Mock    → Enforces expectations

🧩 Dummy

Intent

Fill a required parameter that is never used.

Key Traits

  • No behavior
  • No assertions
  • Often null, empty object, or placeholder

Use When

  • The SUT requires a dependency irrelevant to the test

Red Flag

  • The test starts depending on it

📤 Stub

Intent

Provide predefined answers to control execution paths.

Key Traits

  • Input → output
  • No verification
  • Passive

Use When

  • You need deterministic data
  • You want to avoid slow or unstable dependencies

Red Flag

  • You start asserting how many times it was called

🏗️ Fake

Intent

Provide a working but simplified implementation.

Key Traits

  • Real logic
  • Often in-memory
  • Deterministic and fast

Use When

  • Replacing infrastructure (DB, cache, queue)
  • You want realistic behavior without real I/O

Red Flag

  • Fake becomes as complex as production code

👀 Spy

Intent

Observe what happened after execution.

Key Traits

  • Records calls and arguments
  • Assertions happen after execution
  • Flexible

Use When

  • Verifying side effects
  • Observing interactions without strict contracts

Red Flag

  • Assertions depend heavily on internal implementation

🔒 Mock

Intent

Enforce interaction contracts upfront.

Key Traits

  • Expectations defined before execution
  • Automatically verified
  • Strict

Use When

  • Testing collaboration rules
  • Preventing forbidden calls
  • Protocol or orchestration testing

Red Flag

  • Refactors break tests without behavior change

🔍 Spy vs Mock

AspectSpyMock
Expectations definedAfter executionBefore execution
Failure timingAssertion phaseVerification phase
StrictnessLowHigh
Refactor resistanceHigherLower

⚠️ Common Misconceptions

“Mocks are bad”

→ Over-mocking is bad. Mocks are valid when enforcing contracts.

“Unit tests must mock everything”

→ Unit tests isolate behavior, not necessarily classes.

“Stub = Mock”

→ Stub controls data. Mock enforces interaction rules.

🧠 Practical Heuristic

		        ┌─ Dummy (irrelevant)
Dependency ─┤
						└─ Relevant ──► Fake → Stub → Spy → Mock

Prefer this order:

Fake → Stub → Spy → Mock

Ask yourself:

  • Replace infrastructure? → Fake
  • Control data? → Stub
  • Observe effects? → Spy
  • Enforce rules? → Mock

🧠 Mental Model

Good tests describe what the system does,

not how it is implemented.

The more your test doubles encode implementation details, the more fragile your tests become.
